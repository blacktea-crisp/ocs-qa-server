## 一、托盘程序（Tray）

### T1. 配置界面输入框错位
- **现象**：托盘「⚙ 配置…」窗口中，标签与输入框未对齐，宽度不一致导致视觉错位。
- **根因**：现用 `pack()` + 固定 `width=14` 的 Label 堆叠，跨行宽度不统一。
- **方案**：改用 `ttk.Grid` 两列布局 —— 第 0 列（标签）统一最小宽度并右对齐，第 1 列（控件）`sticky="ew"` 拉伸；统一 `rowconfigure` 行高与 `padx/pady`；窗口设 `minsize` 防挤压；提示文字跨两列显示。
- **验收**：所有字段左边界、输入框右边界严格对齐；缩放不破版。
- **目标版本**：0.2.0

### T2. 无 API Key 输入
- **现象**：0.1.0 初版托盘的配置窗口缺少「API Key」项（早期已补，需回归确认）。
- **方案**：确认存在 `LLM_API_KEY` 密码框（`show="•"`）+「显示/隐藏」切换；留空=保持原值不改；已设置时占位提示「已设置（留空则保持不变）」。与网页端保持一致。
- **验收**：可填写云端 key 并保存生效（后端 `effective_llm()` 读取）。
- **目标版本**：0.1.x 补丁 / 0.2.0（回归确认）

### T3. 无「设置页测试连接」
- **现象**：无法在托盘里验证云端 base_url/api_key 是否可用。
- **方案**：配置窗口加「测试连接」按钮，调用后端新增接口 `POST /api/admin/llm/test`（后端用当前有效配置发一条极简 `chat` 请求，返回 `{ok, model, latency_ms, error}`）。前端展示连通结果。
- **验收**：正确配置返回成功+模型名+耗时；错误 key/地址返回明确错误信息。
- **目标版本**：0.2.0

### T4. 无「提供商配置快捷切换」（命名 / 编辑 / 删除）
- **现象**：只能在 base_url/model/key 上反复手填，无法保存多套「提供商配置」并一键切换。
- **方案**：
  - 数据：新增表 `llm_profiles(id, name, provider, base_url, api_key, model, vision_model, is_default, created_at)`。
  - 接口：`GET/POST/PUT/DELETE /api/admin/llm/profiles`，`POST /api/admin/llm/profiles/{id}/activate`（设为当前生效）。
  - UI：托盘配置窗口顶部加「配置档案」下拉 + 「新建/保存为/删除」按钮；选择档案即套用其字段。
  - `effective_llm()` 优先读「当前激活的 profile」，回退 `settings_kv`，再回退 `.env`。
- **验收**：可创建多套（如「本地 Ollama」「OpenAI」「某中转」），命名、编辑、删除、一键切换均生效。
- **目标版本**：0.2.0

### T5. 无「获取模型列表并快捷选用」
- **现象**：模型名需手填，易错。
- **方案**：后端新增 `GET /api/admin/llm/models`（调 OpenAI 兼容 `GET {base_url}/models`，用当前 key）；前端/托盘加「获取模型列表」按钮，下拉选择后回填 `model`（及可选 `vision_model`）。请求失败给出提示。
- **验收**：点一次即列出 provider 支持的模型并可点选填入。
- **目标版本**：0.2.0

## 二、网页管理台（Web Admin）

### W1. 无「设置页测试连接」
- 与 **T3** 同一后端接口 `/api/admin/llm/test`；设置页加「测试连接」按钮，展示结果。目标 0.2.0。

### W2. 无「提供商配置快捷切换（命名/编辑/删除）」
- 与 **T4** 同一套 `llm_profiles` 表与接口；设置页做成「档案」下拉 + 表格管理（增删改 + 激活）。目标 0.2.0。

### W3. 无「获取模型列表并快捷选用」
- 与 **T5** 同一 `GET /api/admin/llm/models`；设置页「获取模型」按钮 + 下拉。目标 0.2.0。

### W4. 运行中"启动"按钮仍然存在且为绿色，启停按钮需整合为两态
- **现象**：Dashboard 服务卡片同时显示 `启动`(绿)/`停止`/`重启` 三个并列按钮；运行中时「启动」仍是绿色可点，语义矛盾。
- **方案**：
  - 合并为**单一两态主按钮**：服务**停止时**显示绿色「▶ 启动」，**运行时**显示红色「■ 停止」；
  - 「重启」降级为次要按钮（或在运行时才出现）；
  - 按钮状态与后端真实状态（经 supervisor `/status`）联动，定期刷新。
- **验收**：任一时刻只有一个主按钮且状态正确；运行中不出现「启动」。
- **目标版本**：0.2.0

### W5. 题库列表答案/选项被截断，且无省略号；需详情页
- **现象**：`questions.html` 用 `slice(0,24/40/60)` 硬截断，无 `…`，且无法查看完整内容。
- **方案**：
  1. 列表截断统一走工具函数 `truncate(text, n)`：超长时保留前 n 字 + `[…]`（明确标注被截断）。
  2. **新增单开详情页** `ocs-admin-ui/question.html?id=<qkey>`：完整展示题干、全部选项、所有答案候选（状态/来源/置信度/命中次数/时间）、该题相关日志；支持在详情页内**进行管理**（转正/降级/删除/新增候选）。
  3. 列表行「管理」按钮跳转到详情页。
- **验收**：列表超长内容带 `[…]`；点击进入详情可看完整信息并管理。
- **目标版本**：0.2.0

## 三、日志（Logging）

### L1. 日志不够详细
- **现状**：`request_steps` 已记录 stage / input / output / latency / ok / error，但展示与字段仍不够细。
- **方案**：
  - 明细补充：每步 `title`（中文说明）、HTTP `status_code`、请求/响应体字节数、`exception` 堆栈、LLM `raw` 原文（已存 response 中，前端可展开）。
  - 前端日志页：新增**筛选**（按 stage、是否失败、时间范围、是否命中题库）、**单请求完整时间线**（已有 `/logs/{id}` 回放，增强展示，原始 JSON 可折叠）、**日志导出**（CSV/JSON）。
- **验收**：任一请求可看到逐步骤完整证据链并导出。
- **目标版本**：0.2.0

## 四、数据库与数据类型扩展性（重点）

### D1. 题型写死四类，扩展性不足
- **现状**：`pipeline.VALID_TYPES = {single, multiple, judgement, completion, unknown}`；`questions.type` 为 TEXT；答案存单个字符串 `answer`；选项存 `options_json`(TEXT)。
- **问题**：新增题型（排序题、匹配题、编程题、连线题…）需改代码多处；答案结构单一（多选靠 `#` 拼、填空靠 `#` 拼）不利于结构化处理与统计。
- **推荐方案（结构化演进）**：
  1. **题型注册表**：新增表 `question_types(code PK, name, answer_schema, enabled)`，内置四类 + `unknown`；`questions.type` 逻辑引用（保留 TEXT 兼容）。新题型只需插入一行 + 定义 `answer_schema`（JSON Schema 描述答案结构）。
  2. **答案结构化**：`answers` 增加 `answer_json TEXT`，按题型存结构化答案：
     - 单选：`{"option_ids":["A"]}` 或多选 `{"option_ids":["A","C"]}`
     - 判断：`{"value": true}`
     - 填空：`{"blanks":["H2O"]}`
     保留 `answer` 文本作为**对外 OCS 输出兼容**（多选用 `#` 拼接、填空用 `#`）。返回 OCS 时由 `answer_json` 渲染成文本。
  3. **选项独立表**：`options(id, qkey, idx, content, is_image)` 取代裸 `options_json`，方便统计/图片题/去重；`questions.options_json` 保留为快照兼容。
  4. **迁移与兼容层**：启动时检测旧库，自动把 `options_json` 迁到 `options` 表；读写走兼容层，旧数据仍可用。
- **验收**：新增一种题型只需注册一行 schema 即可录入/存储/返回；旧数据无损。
- **目标版本**：0.2.0（数据模型重构，需迁移脚本）

## 六、OCS 接入：识图配置

### O1. ocsjs 显示「当前配置不支持识图」
- **现象**：导入 OCS 的题库配置被判为不支持识图。
- **根因**：导出的 `AnswererWrapper` 未声明图片题优化 —— OCS 判定"支持识图"的条件是：`method: post` 且 `data` 中引用了 `${images}` / `${suggestion_title}` / `${suggestion_options}`（见 ocsjs `isAnswererWrapperSupportImageOptimize`）。0.1.0 导出的配置是 `get` 且不含这些字段。
- **方案**：
  - `scripts/export_ocs_config.py` 增加 **v2 导出模式**：生成 `"v": 2` 的配置，`method: post`，`data` 包含 `title/type/options` 及 `images`（字段用 `${images}` 或自定义 handler 把 `env.images` 传入）。
  - 后端 `/search` 已支持 `images`（POST body），确保接收并落库/送识图。
  - 文档 `docs/OCS_INTEGRATION.md` 说明 v1（纯文本）与 v2（含识图）两种配置的差异与选用。
- **验收**：使用 v2 配置时 OCS 不再提示不支持识图，图片题能触发识别。
- **目标版本**：0.2.0
